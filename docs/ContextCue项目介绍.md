# ContextCue 项目介绍

> 文档日期：2026 年 10 月 25 日。本文适用于项目汇报、课程展示和团队说明，包含产品总体设想、第一阶段建设内容及 AI 预测扩展方向。功能定位不等于实现进度，实际进度见第十一节。本文不变更已确认的开发范围、公共接口或成员分工。

## 一、项目概述

ContextCue 是一款面向 HarmonyOS 平台的智能场景提醒应用，围绕“在合适的时间、合适的地点，提醒用户完成合适的事情”展开设计。

日常生活中，遗忘往往与具体情境相关：到了实验室才发现忘带电脑，经过快递站却忘记取件，到了约定时间仍未处理待办。ContextCue 将时间、地点和自然语言输入结合起来，让用户能够用更贴近日常表达的方式建立提醒，并在条件满足时收到系统通知。

项目的建设分为两个层次：第一阶段完成用户明确提出的提醒，包括手动创建、自然语言创建、条件触发和数据管理；后续探索 AI 预测能力，在用户授权范围内分析场景和历史记录，提出用户可能需要的提醒建议。

项目的长期目标是从“记录用户已经想到的事情”，逐步发展为“帮助用户发现值得提前准备的事情”。预测结果应作为建议交由用户确认，不能把模型推测当作用户已经安排好的任务。

## 二、项目背景与目标用户

### 2.1 需要解决的问题

- 创建提醒时，逐项填写内容、时间和地点比较繁琐。
- 单纯的时间提醒不能表达“到实验室后再提醒”等场景需求。
- 单纯的地点提醒不能表达“下午两点以后到实验室再提醒”等联合条件。
- 用户可能已经安排好行程，却没有主动想到需要携带的物品或需要提前完成的准备。
- 提醒数据、触发逻辑和通知处理如果各自独立实现，容易出现格式不一致、重复通知和状态混乱。

### 2.2 目标用户

ContextCue 初期主要面向学生、科研学习人员及日常有多场景待办需求的用户。例如，需要在教室、实验室、宿舍、办公室或快递站之间切换，并管理学习、工作和生活事项的人群。

### 2.3 建设目标

1. 用统一数据模型管理不同来源和不同触发方式的提醒。
2. 降低提醒创建成本，支持自然语言输入。
3. 在时间与地点条件满足时触发提醒，提高提醒与当前任务的相关性。
4. 明确区分提醒已通知与事项已完成，保留用户对任务状态的控制。
5. 为未来 AI 预测建议提供可扩展的业务基础。

## 四、第一阶段核心功能

### 4.1 时间提醒

用户指定一个时间和提醒内容，到达时间后触发通知。

示例：“明天下午两点提醒我提交实验报告。”

系统需要识别事项与时间，创建 `TIME` 类型提醒。相对时间的解释以解析时刻和明确的时区为依据；如果时间不清楚，应要求用户补充。

### 4.2 地点提醒

用户指定目标场景和事项，进入目标区域时触发提醒。

示例：“到快递站时提醒我取快递。”

应用通过用户保存的 Scene 表示地点，并使用稳定的场景 ID 关联提醒。第一阶段正式支持进入场景的 `ENTER` 语义；离开场景的 `EXIT` 仅在模型中预留，不作为当前已完成能力介绍。

### 4.3 时间与地点联合提醒

用户同时指定时间与目标场景，创建 `BOTH` 类型提醒。联合条件采用 AND 语义：时间已到，并且用户当前位于目标场景，才允许发送最终通知。

示例：“明天下午两点以后到实验室时，提醒我检查实验数据。”

- 时间到达时已经在实验室，可以触发。
- 时间到达时不在实验室，等待之后进入实验室。
- 时间到达前曾经进入、但到达时已经离开，不能把历史进入事件继续当作地点条件满足。

### 4.4 AI 自然语言创建提醒

用户直接输入一句日常表达，AI 解析其中的事项、时间、地点和触发类型，生成统一的创建草稿。

示例：“明天下午两点去实验室，提醒我带电脑。”

系统可以识别“带电脑”这一事项、“明天 14:00”这一时间以及“实验室”这一场景。但“带电脑”可能更适合出发前提醒，句子本身不一定明确了触发时机，因此应用应展示解析结果供确认，必要时询问用户是提前提醒，还是到达后提醒，不能擅自补全业务含义。

AI 返回结果分为三类：

| 状态 | 含义与处理 |
| --- | --- |
| READY | 已形成可供用户确认的创建草稿，确认后调用提醒服务创建 |
| NEEDS_CONFIRMATION | 时间、地点或语义存在不确定性，需要补充或修改 |
| FAILED | 网络、供应商调用或解析等失败，按错误类别决定能否重试 |

自然语言解析本身不保存提醒，不直接注册系统触发器，也不发送通知。用户确认后，由 ReminderService 统一创建正式提醒。

### 4.5 提醒数据管理

应用需要支持提醒的创建、查询、编辑、启用、禁用、完成和删除，并统一维护提醒状态。

提醒“已触发”表示通知已经成功发送；“已完成”表示用户主动确认事项完成。这两个状态不同，例如收到提交报告的提醒，不意味着报告已经提交。

第一阶段的公共规则围绕一次性提醒设计。每日、每周、工作日等周期规则属于后续单独扩展内容。

### 4.6 系统通知

时间模块和地点模块上报条件事件，由 TriggerCoordinator 统一判断后调用通知端口。通知成功后再更新为已触发；通知失败不能假装成功或提前把事项标为完成。

重复事件需要去重。通知已经发出但状态保存失败时，仍存在重试导致重复调用通知端口的风险，正式通知适配器与持久化集成需要共同处理这一边界。

## 五、AI 预测提醒：后续扩展方向

### 5.1 功能定位

AI 自然语言创建处理的是用户已经明确说出的任务；AI 预测则尝试提出用户尚未主动创建、但在当前情境下可能有价值的提醒。

例如，用户主动输入“下午去实验室”，自然语言模块可以整理这条安排；预测模块进一步分析用户允许使用的上下文，可能提出“是否需要提前提醒携带电脑和实验记录本？”这一建议。

ContextCue 不应宣称能够判断用户是否真的遗忘了某件事。预测结果表达的是可能的准备需求，不能把未记录的行为当作未完成，也不能把用户未确认的推测变成正式待办。

**AI 预测当前尚未实现，不属于第一阶段验收范围。以下内容是产品扩展设想，正式开发前需要另行确认需求、数据来源和验证方式。**

### 5.2 可能覆盖的场景

| 场景 | 可参考的信息 | 建议示例 |
| --- | --- | --- |
| 实验或课程准备 | 用户已确认的安排、场景及主动保存的准备清单 | “下午有实验安排，是否提前提醒检查实验用品？” |
| 常用场景准备 | 用户主动提供的场景清单与历史提醒 | “这次去实验室是否需要携带电脑？” |
| 出行准备 | 用户录入的行程及明确选择的物品清单 | “明天准备出行，是否创建证件检查提醒？” |
| 待办衔接 | 应用中尚未完成的事项与相关场景 | “还有一项取件待办，是否添加快递站提醒？” |

以上场景只说明潜在交互，不代表应用当前能够读取课程表、日历、行程或其他应用数据。任何新增数据源都需要独立接入、明确授权和必要的校验。

### 5.3 预测所需的信息

优先考虑使用用户主动输入、已经保存在应用内且同意用于预测的数据：

- 已创建的提醒内容、时间和目标场景。
- 用户主动确认的完成情况，以及是否接受过某类建议。
- 用户保存的常用地点与准备清单。
- 用户主动填写的场景偏好。

定位和外部日历等数据只能在确有功能需要且用户明确授权后使用。不能默认收集连续位置轨迹，也不能将没有定位结果解释为用户没有到达目标地点。

### 5.4 建议处理流程

预测能力计划采用“提出建议、用户确认、再创建提醒”的流程：

1. 汇总用户允许使用的必要上下文，标明哪些是事实、哪些信息缺失。
2. 生成少量与当前安排有关的候选建议，并附上可理解的理由。
3. 检查是否与已有提醒重复、时间是否合理、地点是否可解析。
4. 展示建议，让用户选择接受、修改、忽略或关闭此类建议。
5. 用户接受后转成统一的 CreateReminderInput，经 ReminderService 校验并创建。
6. 之后继续使用现有时间、地点、协调器和通知链路。

预测建议与正式提醒应分开管理。当前版本不为预测擅自扩展公共枚举或创建一套新的 Reminder；建议记录及来源追踪等字段应在后续正式设计时统一评审。

### 5.5 误报控制与用户控制

预测提醒的目标是提供有用的建议，同时控制打扰：

- 低依据的建议不应直接推送为正式提醒。
- 同类建议应有频率限制，允许用户关闭或不再推荐。
- 已存在的提醒、已完成的事项和被明确拒绝的建议，应参与去重与过滤。
- 模型给出的自评置信度不能直接当作真实准确率，阈值需要通过测试样本校准。
- “通常要带某物”应标注为通用建议，“你过去创建过某条提醒”才能作为个人历史依据，二者不能混淆。

### 5.6 评价方式

未来可以从建议接受率、有效反馈率、重复建议比例、用户关闭比例和场景相关性等方面评估预测质量。用户忽略建议不等于建议错误，接受建议也不等于已经证明避免了遗忘，因此需要结合明确反馈和场景测试进行分析。

当前没有预测准确率或减少遗忘比例的实测数据，不应在汇报中给出未经验证的百分比。

## 六、总体技术架构

ContextCue 采用公共领域层与功能模块分离的结构，核心关系如下：

```text
用户手动输入 / 自然语言输入
              ↓
       创建输入 / AIService
              ↓
  用户确认 + CreateReminderInput
              ↓
       ReminderService
          ↙        ↘
ReminderRepository  时间 / 地点端口
                          ↓ 条件事件
                  TriggerCoordinator
                          ↓
                 系统通知端口
                          ↓ 通知成功
             由 ReminderService 更新状态
```

未来预测模块位于创建入口之前，输出候选建议；用户接受后仍进入同一条创建与触发链路。

主要模块职责：

| 模块 | 职责 |
| --- | --- |
| model | 唯一的 Reminder、Scene、创建输入、枚举及结果结构 |
| ai | 自然语言解析、供应商适配、结构与语义校验、创建输入映射 |
| service | 提醒业务入口、校验、状态转换和触发注册协调 |
| repository | 提醒保存与查询的抽象及实现 |
| reminder/contract | 时间、地点、通知、场景解析及条件事件的共同契约 |
| TriggerCoordinator | TIME、LOCATION、BOTH 的最终触发判定 |
| pages / components | 用户界面、输入和交互 |
| reminder/time / notification | 正式时间调度与系统通知能力 |
| location | Scene 管理、定位、围栏及地点条件判断 |

## 七、统一数据模型与状态管理

Reminder 至少包括唯一 ID、事项内容、触发类型、可选触发时间、可选场景引用、状态、来源和创建时间，并记录触发与完成时间。

当前状态包括 ACTIVE、DISABLED、TRIGGERED、COMPLETED。启用与完成行为通过状态表示，避免不同模块分别维护互相矛盾的布尔字段。

时间戳统一使用 Unix Epoch 毫秒。提醒通过 sceneId 关联场景，场景名称用于展示；经纬度、半径和围栏参数由地点模块维护，不在提醒实体中重复保存。

无论提醒由手动输入还是 AI 生成，都使用相同的 CreateReminderInput，经服务校验后形成统一 Reminder，避免页面、AI 和系统模块之间反复转换不同格式。

## 八、AI 接入与可靠性设计

当前 AI 流程已经按职责拆分为模型调用、JSON 提取、字段校验、场景名解析和数据映射。供应商通过 AIModelProvider 接入，业务侧不直接依赖某个模型的请求格式。

华为云 MaaS 是已选定的服务方向，deepseek-v4.1-flash 为候选模型。服务尚待实际开通，正式模型和端点以控制台为准；现阶段代码使用 Fake Provider 验证链路，不能据此宣称真实模型效果已经达标。

可靠性处理重点包括：网络和服务错误允许适当重试；结构或字段错误明确提示；时间和地点不确定时要求确认；不自动把过去时间平移到未来；用户确认时重新校验时间，防止过期草稿被正式激活。

## 九、隐私与安全设计原则

应用涉及用户事项和地点信息，需要遵循按需使用与用户可控制的原则：

- API Key、Secret、Token 不写入源码、不提交 GitHub。
- 正式服务优先考虑由后端代理保管长期供应商凭证，避免随客户端打包。
- 发送到模型的上下文限于完成当前解析或建议所需的信息，避免默认上传连续位置记录和完整历史。
- 定位、通知及外部数据源按实际需要申请授权，并提供权限缺失时的提示。
- 预测能力应提供独立开关与数据清理机制，其具体策略需要在后续实施中落地。
- 日志不能包含密钥、完整认证请求头或不必要的用户内容。

以上是设计原则，其中后端代理、预测开关和预测数据治理等内容尚未全部实现，不能作为当前已具备的安全功能宣传。

## 十一、当前开发进度

截至本文编写时，feature-ai 已完成公共模型、ReminderRepository 契约与内存实现、ReminderService、公共触发契约、TriggerCoordinator，以及 Fake AI Provider、Parser、Validator、Mapper 和 DefaultAIService。

最近一次本地测试报告为 79 项通过、0 失败、0 错误；debug HAP 构建成功，产物未签名。验证包含真实业务模块之间的联调，时间、地点和通知采用测试替身。

79 项测试通过不能代替真实模型评测、正式系统能力验收或 API 24 真机验证；本文也不据此判断其他功能分支的完成情况。

## 十二、实施路线

1. **公共基础与可测业务链路**：统一数据、服务、端口和 Fake AI，建立单元及集成测试。该部分已有代码基础。
2. **第一阶段系统集成**：在 develop 接入正式 UI、时间、地点和通知能力，验证完整业务闭环。
3. **真实 AI 接入**：在完整链路稳定后接入 MaaS，验证模型效果、错误处理、成本和安全配置。
4. **稳定性与数据保障**：完善持久化、恢复、去重和真机验证，与集成工作协同推进。
5. **AI 预测扩展**：优先验证少量、可解释、用户确认的提醒建议，逐步评估是否值得扩大场景。

## 十三、项目特色与预期价值

ContextCue 的特色在于将场景条件与提醒业务结合，并通过自然语言入口降低创建负担。统一 Reminder 和触发协调机制使多个功能模块能够共享同一套规则，也为未来 AI 预测建议提供稳定的接入基础。

对于用户，项目希望减少多场景切换中的待办遗漏和重复录入；对于团队，项目提供了一次完整的 HarmonyOS 开发实践，覆盖 ArkTS、ArkUI、系统能力适配、AI 输出校验、模块解耦、自动化测试和 GitHub 协作。

项目最终希望形成一款可理解、可控制的场景提醒工具：基础版本把用户明确提出的任务可靠地记录和触发，扩展版本在用户授权下提供适量的准备建议，让提醒逐步贴近实际生活情境。
