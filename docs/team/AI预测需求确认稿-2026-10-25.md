## 1. 一句话讲清楚预测是什么

**在用户已经创建的安排旁边，系统主动问一句："要不要顺便加个提醒？"——仅此而已。**

对比：

| | 现在（第一阶段） | 加了预测之后 |
| --- | --- | --- |
| 谁想到要提醒 | 用户自己 | 用户自己 + 系统提个醒 |
| 系统做什么 | 用户说什么记什么 | 看到用户记了"明天去实验室"，多问一句"要不要提醒带电脑？" |
| 创建提醒的人 | 用户点确认 | **仍然是用户点确认**，系统永远不代替用户创建 |

所以"预测"这个词听起来大，实际产品形态就是**一张可以拒绝的卡片**。

## 2. 用户完整剧本（小李的故事）

### 第一幕：建议出现

1. 小李输入"明天下午两点去实验室"，点保存。
2. 提醒创建成功。保存成功页的下方，出现一张建议卡片：

```text
┌──────────────────────────────────────┐
│ 💡 要不要也提醒带电脑？               │
│                                      │
│ 理由：你近 5 次去实验室的提醒里，     │
│ 3 次包含"带电脑 / 实验记录本"。       │
│ （依据：你的历史提醒）                │
│                                      │
│ [接受]  [修改]  [忽略]  [不再提示]    │
└──────────────────────────────────────┘
```

3. 四个按钮的效果：

| 按钮 | 发生什么 |
| --- | --- |
| **接受** | 立即按卡片内容创建一条正式提醒（来源标 AI），之后和时间/地点提醒完全一样：到点通知、可完成、可删除 |
| **修改** | 打开预填好的编辑页，小李改成"带电脑和实验记录本"再保存 |
| **忽略** | 卡片收起，本次什么都不发生（系统记一次"忽略"，用于降低这类建议的频率） |
| **不再提示** | 以后"去实验室 + 带电脑"这个组合永远不再建议（可在设置里恢复） |

4. 如果小李不需要任何建议：设置页有一个"提醒建议"总开关，关掉后上面的一切都不会出现。

### 第二幕：没有历史数据的新用户

新用户第一次去健身房，系统没有任何历史，但可以给**通用建议**：

```text
│ 💡 要不要也提醒带毛巾和水杯？         │
│ 理由：去健身房常需要携带这些。        │
│ （通用建议，非你的个人历史）          │
```

注意理由文案必须标注"通用建议"——**"你过去如何"和"大家通常如何"是两种依据，永不在文案里混淆**（项目介绍 5.5 节的明文要求）。

### 第三幕：最坏情况

即使引擎判断全错，用户的体验上限是：**每天最多看到 3 张卡片、零系统推送、零自动创建的提醒**。预测功能在物理上不可能替用户做任何决定。

## 3. 建议的一生（生命周期）

一条建议是一个独立的小记录（叫 `Suggestion`），和提醒（`Reminder`）是**两个东西**：

```text
PROPOSED（已生成，等待用户看）
   ├──→ ACCEPTED（接受了）→ 变成正式 Reminder，建议存档
   ├──→ MODIFIED（改了后接受）→ 按改后的内容变成 Reminder，建议存档
   ├──→ IGNORED（忽略了）→ 存档，计一次忽略
   └──→ DISMISSED（不再提示）→ 存档，该组合进入拒绝名单
```

规则：

- 建议**永远不会**变成 ACTIVE 提醒，除非用户点了"接受"或"修改后保存"。
- 变成 Reminder 后，建议记录保留（用于统计），但不再展示。
- 48 小时没看的建议自动过期，不再展示（不计入忽略）。

## 4. 建议的内容从哪里来（三种来源，按优先级）

### 4.1 准备清单（最可信，用户自己写的）

用户可以在某个 Scene 下自己维护一个"去这儿常带什么"清单。命中即建议。

- 例：小李在"实验室"的清单里写了 [电脑、实验记录本、门禁卡]。他创建去实验室的提醒时，系统检查这三样是否已在提醒内容里，缺的就建议。
- 理由文案："来自你的实验室准备清单"。
- 这是完全确定性的匹配，不需要任何 AI。

### 4.2 历史规律（次可信，从用户自己的提醒里统计）

系统统计：**去某个场景的历史提醒里，某件物品出现过多少次**。

具体算例（初始阈值：样本 ≥ 3 次、出现率 ≥ 60%）：

```text
小李的提醒历史里，目的地 = 实验室 的提醒共 5 条：
  ① 带电脑            → 含"电脑"
  ② 带实验记录本      → 含"实验记录本"
  ③ 交实验报告        → 不含物品
  ④ 带电脑和记录本    → 含"电脑"
  ⑤ 检查数据          → 不含物品

"电脑"出现 3/5 = 60% ≥ 60%，样本 5 ≥ 3  → 达标，生成候选"带电脑"
"实验记录本"出现 2/5 = 40% < 60%        → 不达标，不生成
```

- "带电脑"和"带笔记本"算同一件东西吗？这一步叫**语义归并**：P2 阶段先用一个小的关键词对照表（电脑/笔记本→电脑），P3 接入模型后由模型做归并。
- 理由文案："你近 N 次去 X 的提醒里，M 次包含……（依据：你的历史提醒）"。

### 4.3 通用模板（兜底，常识）

内置一张很小的模板表（先只做 5-8 个场景），新用户或无历史时使用：

| 场景 | 通用物品 |
| --- | --- |
| 健身房 | 毛巾、水杯 |
| 实验室 | 电脑 |
| 图书馆 | 借书证、要还的书 |
| 快递站 | 取件码 |
| 机场/车站 | 身份证、充电宝 |

- 理由文案必须带"通用建议，非你的个人历史"标注。
- 模板表是硬编码配置，由组长维护，不联网更新。

**优先级：清单 > 历史 > 模板。** 同一件物品只会用最高优先级的理由生成一张卡片，不重复轰炸。

## 5. 系统怎么工作（分层，每层一句话）

```text
① 事件钩子（什么时候算一次）
     只在三个时机运行：用户刚创建了一条带场景的提醒 / 用户刚完成一条提醒 / 用户打开应用
     —— 不是后台定时轮询，不挂在定位上，不用的时候一行代码都不跑

② 信号层（用什么算）
     提醒历史 + 完成记录 + Scene 清单 + 准备清单 + 建议交互日志（第 7 节）

③ 候选层（算出"可以提什么"）
     规则引擎：做 4.1/4.2/4.3 三种确定性匹配 —— 永远可用
     模型引擎：只做语义归并和理由润色 —— MaaS 就绪后才启用，挂了不影响规则引擎

④ 策略闸门（决定"哪些真的展示"）
     见第 6 节，全部在展示之前执行

⑤ 展示（用户看到卡片）
     应用内卡片，四选一 —— 绝不推送、绝不打扰锁屏

⑥ 创建（用户点了接受）
     走现有公共链路：CreateReminderInput → ReminderService → 校验 → 触发注册
     和手动创建、AI 解析创建走的是同一条路，没有任何特殊通道
```

## 6. 误报控制（策略闸门，参数表）

所有闸门在建议**展示之前**执行，全部初始值待校准：

| 闸门 | 初始值 | 说明 |
| --- | --- | --- |
| 每日上限 | 3 条/天 | 超出的候选直接丢弃，不排队到明天 |
| 同组合冷却 | 7 天 | "实验室+电脑"被忽略后，7 天内不再出现 |
| 重复检查 | 有则不提 | 已存在内容相似的 ACTIVE 提醒时，不再建议同一件事 |
| 拒绝名单 | 永久 | DISMISSED 的组合不再建议，设置里可查看和恢复 |
| 样本门槛 | ≥3 次 且 ≥60% | 历史规律的最低置信条件 |
| 过期 | 48 小时 | 没人看的建议自动作废 |
| 总开关 | 默认关 | 新用户不开，看了说明自己开 |

## 7. 数据设计（内部结构，待评审）

以下字段全部放在 `prediction/` 模块内部，**不进公共 `model/**`**（红线：不为预测改公共枚举或 Reminder 结构）。P1 阶段评审后冻结。

一条建议记录（示意）：

```json
{
  "id": "sug-0001",
  "sceneId": "lab-1",
  "sceneName": "实验室",
  "itemText": "带电脑",
  "reasonType": "HISTORY",
  "reasonDetail": "近5次去实验室的提醒中3次包含",
  "sourceReminderId": "rem-0231",
  "status": "PROPOSED",
  "createdAt": 1799992800000
}
```

交互日志（每次展示/点击记一条，仅在开关开启时记录）：

```json
{ "time": 1799992860000, "suggestionId": "sug-0001", "action": "IGNORED" }
```

action 取值：`SHOWN / ACCEPTED / MODIFIED / IGNORED / DISMISSED`。这份日志同时服务两件事：给规则引擎当频率依据、给第 11 节的评测当数据源。

## 8. 隐私与开关

- 预测只用**应用内已有**的数据（提醒、完成记录、Scene、清单），不读日历、课表、通讯录，不取连续定位轨迹。
- 总开关默认关闭；关闭时停止一切计算和日志记录，并提供"清空全部建议数据"按钮。
- 接入模型（P3）后，发给模型的内容仅限"当前提醒文本 + 相关场景名"，不发送历史记录全量。
- 理由文案区分"个人历史"与"通用建议"，见第 4 节。

## 9. 与现有架构的关系（给队友的定心丸）

**不动的**：17 个冻结公共文件、`Reminder` 结构、公共枚举、`ReminderService`、`TriggerCoordinator`、触发链——一个字节都不改。

**只加的**：

- `entry/src/main/ets/prediction/` 新目录（建议记录、交互日志、规则引擎、闸门，全部组长负责）；
- 一个建议卡片 UI 组件 + 设置页开关（罗鸿程）；
- 无新增权限、无新增系统能力、无后台行为。

接受建议后的链路和手动创建完全一致，复用全部现有校验（过期时间照样会被拒）。

## 11. 评测怎么做（不拍脑袋）

指标定义（全部基于交互日志，实测后才有数字）：

| 指标 | 定义 |
| --- | --- |
| 接受率 | ACCEPTED+MODIFIED ÷ SHOWN |
| 忽略率 | IGNORED ÷ SHOWN |
| 拒绝率 | DISMISSED ÷ SHOWN（最需要盯的：高了说明在骚扰用户） |
| 重复建议率 | 被重复检查闸门拦下前，内容撞车的候选占比 |

方法：

1. **离线回放集**：组长构造 10 个固定脚本场景（含历史充分/新用户/被拒绝过/已有重复提醒等），规则引擎跑一遍断言输出，作为单元测试——不联网、不依赖模型。
2. **P2 vs P3 对比**：同一批脚本，纯规则版和带模型版各跑一次，看语义归并到底带来多少提升，用数据决定模型引擎的必要性。
3. **汇报口径**：只引用实测数字；模型自评的置信度不算数（项目介绍 5.5 节要求）。

## 14. 红线（不做清单）

1. 不代替用户创建任何提醒。
2. 不发系统推送，建议只在应用内展示。
3. 不读日历、课表、通讯录，不取连续定位轨迹。
4. 不在后台轮询，只在三个事件时机计算。
5. 通用建议与个人历史在文案上永不混淆。
6. 模型自评置信度不作为展示依据，阈值以实测校准。
7. 不为预测修改公共枚举、Reminder 结构或任何冻结接口。
8. 汇报中不使用未实测的百分比；预测在演示中始终标注"扩展能力"。
