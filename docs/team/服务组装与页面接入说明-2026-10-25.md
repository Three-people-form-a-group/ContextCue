## 1. 现在由谁创建服务

| 文件 | 职责 | 谁可以修改 |
| --- | --- | --- |
| `AppServices.ets` | 页面服务集合、依赖配置、组装 ReminderService / AIService / TriggerCoordinator | 组长；公共签名变更须同步成员 |

| `entryability/EntryAbility.ets` | `onCreate` 调用 `initializeAppServices()`，先初始化再加载页面 | 集成公共文件，避免三人同时改 |

组装顺序：建立事件转发入口 → 创建时间/地点适配器 → 创建 ReminderService → 创建 TriggerCoordinator 和 AIService → 连接事件入口 → 发布服务集合。

时间和地点工厂得到同一个 `TriggerEventSink`，因此无需相互依赖，也无需修改现有公共端口的签名。只有完整组装成功后，页面才能取得服务。初始化失败会抛错，不发布半成品，也不会偷偷回退到另一套数据。

同一进程重复初始化直接返回原实例，不重新调用工厂、不清空提醒；页面退出、Ability 销毁时不要清空注册表。进程重启会重新创建服务，当前内存数据会丢失。跨进程/Worker 不共享这份实例，后台系统事件和重启恢复仍须在正式集成时验证。

## 2. 罗鸿程：页面如何获取服务

普通 `pages/*.ets` 中使用（更深层文件按相对路径调整 import）：

```typescript
import { getAppServices } from '../app/AppServiceRegistry';
import { AppRuntimeMode } from '../app/AppServices';
import { ReminderSource, TriggerType } from '../model/ReminderEnums';

const services = getAppServices();
const result = await services.reminderService.findAll();
if (result.success && result.data !== undefined) {
  // 把 result.data 赋给页面自己的响应式列表状态。
} else {
  // 展示 result.error，不把读取失败伪装成空列表。
}

const created = await services.reminderService.create({
  content: '带电脑',
  triggerType: TriggerType.TIME,
  triggerTime: Date.now() + 60000,
  source: ReminderSource.MANUAL
});
if (created.success) {
  // 返回列表并重新查询；失败时展示 created.error，保留表单。
}

if (services.mode === AppRuntimeMode.DEVELOPMENT) {
  // 页面明确展示：开发联调，数据仅保留在本次进程，尚无自动提醒和系统通知。
}
```

以上语句放在页面方法/生命周期内，不放在模块顶层执行。启动前调用 `getAppServices()` 会抛出 `APP_SERVICES_NOT_INITIALIZED`；正式页面不要自行补建服务。独立组件预览尚不具备 Ability 启动流程，可继续用 UI 自己的隔离 Mock 预览。

页面不 `new ReminderService`、不接触仓储、不初始化协调器。列表页、详情页、编辑页用同一入口；详情导航只传 ID，再查询最新数据。服务不是 ArkUI 响应式状态：页面进入、返回前台或操作成功后按需重新查询并更新页面状态。

AI 同样通过 `services.aiService.parseReminder(text, context)` 调用。得到 READY 草稿后，展示给用户确认，再调用上面的 `reminderService.create(draft)`。解析本身不会保存提醒。

## 3. 当前开发适配的能力边界

当前 `AppBootstrap` **明确选择 DEVELOPMENT**，适用于页面联调，不是可交付的系统提醒版本：

- 可以通过真实 ReminderService 创建、查询、编辑、启用、禁用、完成和删除；使用公共校验和状态转换规则。
- 提醒只保存在 `InMemoryReminderRepository`。没有持久化，也没有自动触发、后台运行、定位、围栏或系统通知。
- 时间和位置注册在此模式下仅为无副作用的开发占位。`create` 成功表示联调数据创建成功，不表示系统已安排可靠提醒。页面必须展示开发模式说明。
- 地点当前状态固定为不在范围内，地点名解析返回 NOT_FOUND，不虚构 Scene。
- 默认 Fake AI 的数据集为空，任意自然语言输入都会返回 FAILED，不能把它宣传为 AI 已上线。AI 成功/确认/失败路径已通过注入固定测试数据验证；联调指定样例时由组长配置专用 Fake 数据。
- 通知占位实现会拒绝调用，不会把未发送通知的提醒标为 TRIGGERED。

服务组装已完成；正式时间、定位、通知、持久化与真机验收仍未完成。`INTEGRATED` 仅表示由集成入口提供依赖，不是生产能力或验收通过标志。

## 4. 两位成员交付什么，怎样接入

罗鸿程交付 `TimeTriggerPort` 和 `ReminderNotificationPort` 的实现；兰铮交付 `LocationTriggerPort` 和 `SceneResolver` 的实现。端口签名仍按《公共接口清单》，本次没有修改。

组长在 `AppBootstrap.ets` 中用 `createAppServices(dependencies)` 替换开发工厂：

| 配置字段 | 提供内容 |
| --- | --- |
| `mode` | `AppRuntimeMode.INTEGRATED` |
| `repository` | 集成选定的 ReminderRepository |
| `createTimePort(sink)` | 接收事件入口，返回罗鸿程的时间适配器 |
| `createLocationPort(sink)` | 接收事件入口，返回兰铮的位置适配器 |
| `notificationPort` | 罗鸿程的通知适配器 |
| `sceneResolver` | 兰铮的场景查询实现，与位置模块使用同一场景来源 |
| `aiProvider` | 联调期 Fake Provider；真实供应商接入另按已有计划 |
| `now` | 毫秒时钟函数 |
| `newId` | 与所选存储生命周期匹配、可保证唯一性的 ID 生成函数 |

适配器可在构造函数里接收并保存 `sink`；这是实现建议，不新增对公共接口的强制方法。时间到达或地点进入时，调用：

```typescript
await sink.onConditionChanged({
  reminderId: reminderId,
  condition: TriggerCondition.TIME, // 地点实现用 LOCATION
  satisfied: true,
  occurredAt: Date.now()
});
```

`TriggerCondition` 从 `reminder/contract/TriggerConditionEvent` 导入。两者都不直接发送最终通知，不直接写仓储或标记 TRIGGERED。事件返回失败时由事件来源按约定记录脱敏日志/安排重试，不吞异常伪装成功。

工厂仅构造依赖，不申请权限、不启动监听、不上报事件；监听启动和权限流程由正式集成入口另行安排。组装尚未完成时事件会被拒绝，不会悄悄丢弃。`schedule/register/cancel/unregister` 内不得等待同一提醒的 `sink.onConditionChanged`，以免与服务串行操作形成自等待。通知适配器也不得等待同一 ID 的服务状态修改。系统回调应作为独立事件，在注册与创建流程完成后上报。

运行期间不能热换依赖：重复初始化会保留第一次组装结果。替换正式模块需要修改统一入口并重启应用。正式适配器持有的系统资源、订阅取消、后台恢复和持久化迁移，在模块实际接入时共同验收，不由当前内存组合模拟完成。

## 5. 现在是否继续保留 UI Mock

尚未合入这些公共文件时，继续用独立 Mock 完成模型和导航适配。合入后，实际应用的页面数据访问可以切到 `getAppServices().reminderService`，删除原页面数组/仓储路径，避免两套数据并存。独立预览可以继续保留隔离的 Mock，但不要混进实际应用服务。

- **时间/通知**：罗鸿程的 `createSystemTimePort`（reminderAgentManager）与 `createSystemNotificationPort`；未配置 AI 凭证时 AI 仍为 Fake（开发样例可联调）。
- **地点**：兰铮的 LocationReminderAdapter + SceneCatalog + V2 围栏扩展（`FenceExtensionAbility` 独立进程，持久 fenceId↔reminderId 注册表）。
- **对账**：启动时提醒/围栏双对账（取消无效、补排 ACTIVE、恢复丢失映射）；`EntryAbility.onForeground` 追加 `reconcileOnAppForeground()`——通知授权恢复或围栏状态变化后自动补排/清理，无需重启。

页面接入变化（罗鸿程）：

- `create / update / enable` 现在遵循**创建与投递分离**：注册失败仍返回 `success: true` 并携带 `warnings`（如 `TIME_SCHEDULE_FAILED`："系统通知暂不可用，提醒已保存，开启通知后自动恢复"）。页面须把 warnings 渲染为非阻断提示条，不再按失败弹窗处理；授权恢复后回前台对账自动补排，页面无需自行实现恢复逻辑。
- 保存时间类提醒前建议先调 `notificationManager.requestEnableNotification(context)`——API 12 之后这是唯一把授权真正写入系统通知服务状态库的入口，设置页开关显示"开"不代表状态库是"开"。
- `OperationResult.warnings` 为冻结文件增量字段，详见《公共接口清单》第八节。
