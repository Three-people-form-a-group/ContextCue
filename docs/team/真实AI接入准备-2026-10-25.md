## 一、Provider 输出契约（解析器已按此实现）

- `AIModelProvider.requestParse(text, context)` 返回 `rawResponse` 字符串；JSON 提取、校验、场景解析、映射全部由现有链路完成，正式 Provider 只负责"构造请求 + 调 HTTP + 返回原始文本"。
- 模型输出的五个键：`content`、`triggerType`、`triggerTime`、`sceneName`、`ambiguous`。
- `triggerTime` 必须是带时区偏移的 ISO-8601 字符串（如 `"2026-10-26T14:00:00+08:00"` 或 `"2026-10-26T06:00:00Z"`，两者是同一时刻）或 `null`。禁止让模型自己计算 Epoch 毫秒——日期运算由解析器 `convertIsoToEpochMs` 完成，代码算时间是 100% 可靠的；这也是小模型方案能稳定工作的关键。
- 解析器容错（2026-10-25 起）：markdown 代码块或说明文字包裹可容忍；约定外的多余字段忽略；缺时区偏移的 ISO 串、不存在的日期（2 月 30 日）、越界时分秒返回 `INVALID_TIME` 进入用户确认；Epoch 毫秒数字仍兼容，作为模型违反格式指令时的兜底。
- 提示词中应把"当前时间、星期几、时区"喂给模型，让它只需做"理解 + 拼日期"，不做数值运算。

## 二、System Prompt 草案（正式接入时按 MaaS 实测微调）

```text
你是一个提醒解析助手。用户会给你一句中文，你把它解析成提醒的 JSON。当前时间：{now}（{weekday}，时区 {timezone}，UTC 偏移 {timezoneOffset}）。

只输出一个 JSON 对象，不带 markdown 代码块，不带任何解释文字。JSON 必须恰好包含以下五个键：
1. content：需要提醒用户做的事，去掉"提醒我"等提示词，保留动作本身。
2. triggerType：只能是 "TIME"（按时间提醒）、"LOCATION"（按地点提醒）或 "BOTH"（时间加地点）。
3. triggerTime：触发时间，格式 "YYYY-MM-DDTHH:mm:ss+08:00"（带时区偏移的 ISO-8601）。没有时间时为 null。
4. sceneName：地点名称，只取用户提到的场所词（如 实验室、家、快递站）。没有地点时为 null。
5. ambiguous：布尔值。任何不确定都要设为 true。

时间规则：相对时间（明天、今晚、十分钟后、周五）以提供的当前时间为基准；已经过去的星期几或日期顺延到下一次；无法确定具体时间（如"下周""月底"）或日期不存在时，triggerTime 置 null 并把 ambiguous 设为 true。
歧义规则：如果用户说了地点也说了时间，但句子没有说清是"时间到达就提醒"还是"到达该地点才提醒"（例如"明天下午两点去实验室，提醒我带电脑"更适合出发前提醒），把 ambiguous 设为 true，不要替用户选择。
提取规则：不要添加用户没说的信息，不要改写过去的时间，不要猜测地点对应的真实位置。
```

Few-shot 示例（与评测集标注一致，正式接入时放入提示词）：

```text
用户：明天下午两点提醒我提交实验报告
输出：{"content":"提交实验报告","triggerType":"TIME","triggerTime":"2026-10-26T14:00:00+08:00","sceneName":null,"ambiguous":false}

用户：到实验室时提醒我把实验数据拷贝到服务器
输出：{"content":"把实验数据拷贝到服务器","triggerType":"LOCATION","triggerTime":null,"sceneName":"实验室","ambiguous":false}

用户：明天下午四点到实验室后提醒我检查实验数据
输出：{"content":"检查实验数据","triggerType":"BOTH","triggerTime":"2026-10-26T16:00:00+08:00","sceneName":"实验室","ambiguous":false}

用户：明天下午两点去实验室，提醒我带电脑
输出：{"content":"带电脑","triggerType":"BOTH","triggerTime":"2026-10-26T14:00:00+08:00","sceneName":"实验室","ambiguous":true}
```

## 三、错误映射与超时

正式 Provider 把 HTTP 层错误映射为 `AIProviderFailure`：

| 情形 | code | retryable |
| --- | --- | --- |
| 连接失败、请求超时、429 限流、5xx | `NETWORK_ERROR` | true |
| 401/403（凭证无效）、404（模型或端点不存在）、400（请求被拒） | `PROVIDER_ERROR` | false |
| 200 但响应体为空或结构异常 | `PROVIDER_ERROR` | true（重试一次有意义） |

`DefaultAIService` 已内置服务级超时兜底（默认 15 秒，第三个构造参数可调），超时返回可重试的 `NETWORK_ERROR`。正式 Provider 仍应设置自己的 HTTP 超时，建议不大于服务级预算。任何日志不得输出凭证、完整认证请求头或用户原文。

5. 价格与免费额度（注意贵阳一等区域近期有调价）；记录到本文。

## 六、评测方法（模型选型用数据说话）

- 评测集：`entry/src/test/AIEvalCorpus.test.ets`，31 条中文语料（READY 纯时间 8、纯地点 5、BOTH 5；NEEDS_CONFIRMATION 8；FAILED 3；容错路径 2），基准时刻 2026-10-25T09:00+08:00，每条标注理想模型输出与期望结果。
- 真实模型评测：临时把 `FakeAIModelProvider` 换成真实 Provider 采集 `rawResponse`，统计三个指标——格式合规率（五键齐全且 `triggerTime` 为合法带偏移 ISO 串）、字段准确率（content/triggerType/sceneName 与标注一致）、歧义判断质量（歧义样例是否正确标 `ambiguous=true`）。
- 候选：deepseek-v4.1-flash（现任）与可用的 14-15B 级模型各跑一遍；解析是全应用调用频率最高的 AI 操作，小模型在延迟和成本上占优，但最终以评测数据为准。
